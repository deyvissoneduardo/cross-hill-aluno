## 2. Objetivo da Task
Implementar a porta de dados da feature com comportamento transacional testável, incluindo fake determinístico para regras críticas sem Firestore real.

---

## 3. Descrição Detalhada
- Criar `lib/firebase/agendamentoStore.ts` com interface/porta e implementação Firestore.
- Implementar fake transacional em arquivo de teste ou helper interno de teste.
- Regras obrigatórias na criação: validar elegibilidade, bloquear mesmo telefone/dia ativo, bloquear slot confirmado, permitir pendentes de telefones diferentes no mesmo slot.
- Retornos públicos não podem carregar dados de terceiros.
- A modelagem Firestore deve seguir as coleções descritas na Tech Spec.

### 6.6 Detalhamento dos Casos de Teste

#### CT-014 — Solicitação cancelada não bloqueia nova solicitação
- **Tipo**: service-integration | **Categoria**: regra_negocio
- **Arquivo**: `lib/firebase/agendamentoStore.test.ts` (criar)
- **Invariant**: status `CANCELADO` não conta como solicitação ativa no dia.
- **Owning layer**: `service-integration` | **Real execution boundary**: `fake-store`
- **Pré-condições**: fake store com solicitação cancelada no mesmo telefone/data.
- **Passos**: criar nova solicitação para outro horário no mesmo dia.
- **Resultado esperado**: nova solicitação com `status: "AGUARDANDO_CONFIRMACAO"`.
- **Negative companion**: CT-025.
- **Critérios validados**: CA-10.

#### CT-025 — Store bloqueia mesmo telefone no mesmo dia
- **Tipo**: service-integration | **Categoria**: regra_negocio
- **Arquivo**: `lib/firebase/agendamentoStore.test.ts` (criar)
- **Invariant**: o mesmo telefone normalizado não tem duas solicitações ativas no mesmo dia.
- **Owning layer**: `service-integration` | **Real execution boundary**: `fake-store`
- **Pré-condições**: fake store vazio.
- **Passos**: criar solicitação; tentar criar outra no mesmo dia com mesmo telefone.
- **Resultado esperado**: segunda chamada retorna erro de duplicidade e não cria documento.
- **Negative companion**: CT-014.
- **Critérios validados**: CA-09, CA-12.

#### CT-026 — Store permite pendentes no mesmo slot para clientes diferentes
- **Tipo**: service-integration | **Categoria**: regra_negocio
- **Arquivo**: `lib/firebase/agendamentoStore.test.ts` (criar)
- **Invariant**: pendentes de terceiros não tornam o slot inelegível na frente cliente.
- **Owning layer**: `service-integration` | **Real execution boundary**: `fake-store`
- **Pré-condições**: disponibilidade ativa sem confirmado no slot.
- **Passos**: criar duas solicitações para o mesmo profissional/data/horário com telefones diferentes.
- **Resultado esperado**: ambas retornam `AGUARDANDO_CONFIRMACAO`; retorno não inclui nome/telefone de terceiros.
- **Negative companion**: cenário de slot confirmado.
- **Critérios validados**: CA-07, CA-15.
